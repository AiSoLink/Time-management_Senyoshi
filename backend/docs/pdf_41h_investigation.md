# 拘束時間 41h20m 原因調査メモ

## 事象
- 2運行（3時間未満）を合算したところ、正しくは約20時間強なのに **41時間20分** になった。
- 出庫 2025/09/10 08:02 と 帰庫 2025/09/11 04:42 の組が約20時間40分で、これが「2回」効いて 41h20m になったと推測される。

## 確認したこと（日報_0910_篠田.pdf）

1. **ブロック分割**
   - 運行IDで分割 → ブロックは **2つ**（ID-414515, ID-414651）。
   - 各ブロック内の出庫・帰庫は **1つずつ**（1ブロックに複数はない）。

2. **ブロックごとの採用組（旧ロジック: 先頭の出庫・先頭の帰庫）**
   - ブロック1: 出庫 08:02, 帰庫 14:33
   - ブロック2: 出庫 14:38, 帰庫 04:42
   - いずれも (08:02, 04:42) の組には **なっていない**。

3. **パイプラインの渡し方**
   - `_extract_header_fields(cleaned_block, ...)` に **ブロック単位の** `cleaned_block` を渡している（全PDFの `cleaned` は渡していない）。
   - このPDF・現行コードでは「先頭の出庫・先頭の帰庫」でも正しい2組が取れる。

## 結論
- **このPDFに対して現行のブロック単位の処理では、(08:02, 04:42) が2回採用される経路は再現できなかった。**
- 41h20m が出た当時は、次のいずれかの可能性がある。
  1. **当時の実装**で、何らかの理由で「全PDFテキスト」を渡していた（バグ）。
  2. **別のPDF**や**別のジョブ**（複数PDFの組み合わせなど）で、ブロック境界や出現順が異なっていた。
  3. **アルコール紐づけ**や**マージ**など後段で、出庫・帰庫が上書きされる経路があった。

## 対策（実施済み）
- 出庫・帰庫を「同一運行の対」として取るため、**「最初の出庫」と「その出庫より後に現れる帰庫のうち、拘束時間が最短のもの」** を採用する `_extract_out_in_dt_pair` を導入。
- 1ブロックに複数出庫・帰庫が混在するレイアウトでも、誤って (08:02, 04:42) のような他運行の組を取らないようにしている。

## 再発時に確認するとよいこと
- 該当ジョブの `manual_input_state.json` やログで、各 `run_state` の `merged_header` の 出庫日時・帰庫日時を確認する。
- パイプライン冒頭で「ブロックごとの抽出結果」をログ出力するオプションを入れておくと、次回の切り分けがしやすい。
